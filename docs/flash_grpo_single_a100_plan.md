## 2. 提议的单卡执行配置

按用户“保险情况下取最大配置”的要求，提议以下**上限候选**，完整入口仍须复测：

| 层级 | 提议 |
|---|---|
| 每个prompt的名义group | 1组，8视频 |
| rollout forward microbatch | **4**，一组8视频拆成2个forward块 |
| policy replay geometry | 保持rollout记录的4行分块；不得未经门禁直接缩到1/2 |
| VAE decode microbatch | **1** |
| HPSv3 frame microbatch | 先取已验证保守路径1；全81帧都评分，不只评分最后选中的24帧 |
| 原始视频评分块 | 初始按16视频设计，实际RSS复核后冻结 |
| GPU剩余余量 | 整卡至少16 GiB，考虑其他进程和非PyTorch分配 |
| CPU剩余余量 | 至少24 GiB MemAvailable |
| OOM/资源不足策略 | 只中止/暂停本次任务；不得停止其他服务或改动其显存驻留 |

若完整入口的额外buffer使batch4余量不足，正式启动前回退batch2，不改变group/总量。
不会在已经生成的旧策略池中随意变更replay几何或提高logprob容差来强行通过。

已prepare的Transformer由后端所有，不强行to(cpu)；其约2.7 GiB权重可常驻GPU。
在无活跃graph的阶段边界释放本进程闲置cache；VAE按既有角色策略管理，HPSv3独立服务
评分时上GPU、之后回CPU。重型rollout/replay与reward计算默认串行，不复制多个训练进程。
HPSv3保持持久加载，不能像smoke那样每组重建一个16GB奖励实例。

## 4. 保持工作量和收集/更新节奏

对于公开上限候选，正式运行应：

1. 固定本epoch行为策略，生成/评分全部384视频。分块流式处理原始media，不长期保留全量浮点视频。
2. 保留真实compact transitions、old logprob、conditioning身份、分组/时间步映射和reward标量。
3. 收集完后按原范围计算统计；全局std不能偷偷在每16视频块内重新计算。
4. 再做两次名义192样本的optimizer commit；两次都使用该次收集的旧策略信息，不能夹入新rollout。
5. 微批loss按总有效样本正确归一化，clip/optimizer/EMA按commit节奏触发，不按每个forward块触发。

把2prompt×8=16视频就更新一次，若仍只做596更新，只有9,536视频，少12倍；
若保住114,432视频则变为7,152更新，多12倍，都不能默默当成原实验。

## 6. 当前框架必须先补的执行/接口能力

这些尚未实现，不是现有YAML填几项就能开跑；不在本轮重审Flash算法数学正确性：

1. 默认运行时明确拒绝 `gradient_accumulation_steps != 1`。不能直接填12；需支持384收集、
   两次192样本commit的执行节奏，复用现有算法/模型/recompute，不新建平行训练框架。
2. 现有Flash示例绑定World-R1通用reward严格资源，不是HPSv3。需要真实HPSv3 adapter/service
   协议与真实checkpoint/revision身份，不能冒用旧8e46b1b63498资源或手写假attestation。
3. 默认拒绝EMA parameter view；需CPU LoRA EMA影子、EMA评估快照及恢复状态，可用独立EMA评估进程，
   不必给训练根模型开放EMA view。周期评估必须真跑300prompt/50步，不用20步preview冒充。
4. 384视频float32原始media约138.82 GiB，192视频也约69.41 GiB，尚未计副本。
   当前约167 GiB RAM，必须流式评分后释放media或使用经过验证的有界存储；不能全量堆栈。
   16视频块理论原始media约5.78 GiB，仍需测真实RSS及collator复制峰值。
5. 512长度CPU文本编码实测约214.43秒/单prompt（2线程）。必须用经实际预处理接口支持的冻结缓存，
   或阶段性GPU编码后缓存；不能重复CPU编码拖慢训练。全部20,000prompt正向embedding约78.125 GiB，
   若实现按每prompt重复存negative则接近156.25 GiB，须按实际存储布局预算并分块加载。
6. 恢复必须保存LoRA、optimizer、EMA、RNG、sampler/epoch游标，以及已采集未消费的旧策略池/commit游标。
   checkpoint可更频繁但不增加优化/评估次数；故障重试计算与正式逻辑训练量分开记账。

Wan VAE的 `vae_tiling` 必须设false（现有0.33.1无enable_tiling），不得伪造方法或擅自升级共享环境。

## 7. 实测后的时间外推（纠正此前预算级粗估）

以batch4的稳定模型端口数据：每视频rollout约82.87秒、decode约5.58秒、反传探针约16.28秒。
这不是完整PPO训练周期实测；评估50步按20步模型forward成本线性外推，HPSv3、JPEG/RPC、
磁盘、预处理、完整trainer调度、EMA/checkpoint及共享GPU暂停均尚未计入。

| 工作量口径（均未自动选定） | 仅模型计算外推 |
|---|---:|
| 公开上限：114,432训练视频/596更新 + 4,500评估视频 | **约149.8天，约5个月** |
| 单独的140-update工程参考：26,880训练视频 + 1,200评估视频 | **约35.5天** |

不能把上述模型部分当作完整总期，也不是性能优化后的保证下界；完整入口实测后应更新。
若仅用于敏感性分析，假设HPSv3每帧0.05/0.1/0.2秒（**这些不是实测值**），公开上限还会
分别增加约5.6/11.1/22.3天，140-update参考增加约1.3/2.6/5.3天，其他开销另计。
按当前实现，公开上限应按数月规划；之前的“2–4周”不能用于这个样本量。
350 GPU-hours只等于单卡14.6天预算，不能同时宣称完成了固定114,432视频。
所有估计假设GPU全天可用，分享GPU导致的暂停会进一步延长墙钟。
